# Spike: авто-детект интро и концовок по анализу кадров (issue #16)

**Статус:** завершён. Вывод — **GO с обязательным гейтом валидации на реальных
сериях** (см. «Вывод»). Порог качества зафиксирован ниже.

**Дата:** milestone 0.2.0. **Ветка:** `feat/issue-7-16-frames`.

## Вопрос спайка

Метки интро/рекапов/концовок сейчас приходят из TheIntroDB (ручные/серверные).
Спайк проверяет, можно ли **локально**, анализом кадров с нашего frame tap,
надёжно детектировать:

- **(а)** общий интро-клип сезона — по повторяемости кадров между эпизодами;
- **(б)** концовки/титры — по чёрным кадрам и «титровым» карточкам;
- **(в)** и насколько это совпадает с метками TheIntroDB как ground truth.

Условие из обсуждения задачи: берём её, только если есть реально работающее
решение с измеримым качеством.

## Что построено

Всё — как расширения поверх `frameHub`, ядро плеера и Rust не тронуты.

| Файл | Роль |
|---|---|
| `src/features/player/extensions/introDetectPolicy.ts` | Чистые алгоритмы: dHash 64 бит, Хэмминг, признаки кадра/классификация, детект концовок, поиск повторяющегося клипа, оценка precision/recall против меток в форме TheIntroDB |
| `src/features/player/extensions/introDetectPilot.tsx` | Пилот-расширение: собирает таймлайн хэшей из `ctx.frames` (~2 fps) по эпизодам сессии, сравнивает эпизоды, показывает кандидатов в `settings.menu`, дампит JSON-отчёт в консоль при закрытии файла. Выключен по умолчанию |
| `tests/introDetect.test.ts` | Юнит-тесты алгоритмов + оценка на синтетическом сезоне + сценарии пилота |

Пилот зарегистрирован в `PLAYER_EXTENSIONS` строкой (рецепт §S2.10), тумблер
«Авто-детект интро (пилот #16)» в меню настроек плеера.

## Методы

**(а) Повторяемость кадров между эпизодами.** Каждый сэмпл кадра (≤32×32 из
frame tap) сжимается в 64-битный perceptual hash (dHash: попарные сравнения
яркости соседей по строкам 9×8 сетки). Совпадение кадров — расстояние Хэмминга
≤ 10 бит. Голосование по гистограмме смещений `tB − tA` находит, на каком
офсете клип из эпизода A повторяется в эпизоде B; выигравшее смещение
выравнивает таймлайны, вдоль них тянется непрерывный run совпадений (с
допуском дыр ≤ 2.5 с). Run длиннее 10 с и с покрытием ≥ 50 % — кандидат в
интро. Голоса из хвоста обоих таймлайнов (последние 25 %) отбрасываются —
там обычно лежат общие финальные титры, их и так детектирует (б).
`detectCommonIntros` берёт эпизод-референс и требует пересечения run’ов со
всеми остальными — так холодный старт (cold open) одного эпизода не
растягивает границы.

**(б) Концовки/титры.** Каждый сэмпл классифицируется по трём признакам:
средняя яркость (Rec.709), «плотность текста» (доля ярких пикселей — разреженные
светлые штрихи на тёмном фоне) и низкая детализация (средний градиент яркости).
Классы: `black` / `credits` (тёмная карточка с редкими яркими штрихами, текст)
/ `content`. Детект — хвостовой run классов `black|credits`, доходящий до конца
эпизода (допуск контентных вставок ≤ 3 с), длиной ≥ 5 с. Серединные чёрные
вспышки (фейды) не попадают — run обязан прилегать к хвосту.

**(в) Оценка.** `evaluateSegments` — покадровая сетка предсказаний против
меток в форме TheIntroDB (`startMs`/`endMs`, `null` = от края файла);
совпадение сегмента — IoU ≥ 0.5 либо обе границы в допуске ±3 с. Метрики:
precision / recall / F1 / средняя ошибка границы. `compareToTheIntroDb`
принимает готовый бандл меток (`intro`/`credits`) — форма та же, что отдаёт
`theintrodbApi`, т.е. на реальных данных сравнение делается без адаптеров.

## Выборка и ограничение (честно)

**Реальных серий в среде разработки нет** (нужны файлы/прогон плеера на
библиотеке), поэтому метрики ниже посчитаны на **синтетическом сезоне**:
3 эпизода по 2 мин, реальные 16×16 RGB кадры, прогон через `probeAt` (та же
классификация/хэширование, что в пилоте):

- общий интро-клип 20 с на разных офсетах (8 / 5 / 12 с) — холодный старт
  перед ним в двух эпизодах, recap перед интро во втором;
- чёрные вспышки-фейды в середине эпизодов;
- финал: титровые карточки + чёрные кадры (15 с);
- контент эпизодов — независимый шум (уникальные хэши).

Это **верхняя оценка** на чистых данных: синтетика не моделирует
компрессионные артефакты, слёзы кадра, слегка разрезанное студийное интро,
рекап из кадров самого эпизода (похожие, но не идентичные хэши). Реальные
цифры будут ниже; типичные классы ошибок разобраны ниже.

## Метрики (синтетический сезон)

Прогон: `npx vitest run tests/introDetect.test.ts` (блок «spike evaluation on
a synthetic season» печатает таблицу).

| Сегмент | Precision | Recall | F1 | Ошибка границы (mean abs) |
|---|---|---|---|---|
| Интро (micro по 3 эп.) | 1.000 | 1.000 | 1.000 | 250 мс (полшага сэмплинга 500 мс) |
| Концовки (micro по 3 эп.) | 1.000 | 1.000 | 1.000 | 250 мс |

Поэпизодно цифры совпадают (P=R=1.0, err=250 мс у всех трёх эпизодов).

Проверенные ошибочные режимы (тестами зафиксировано поведение):

- **recap перед интро** — не втягивает в интро: начало сегмента смещено не
  более чем на 1.5 с от истинного (тест «recap before the intro does not
  shift the intro start»);
- **cold open** — уникальный контент перед интро не попадает в сегмент
  (границы интро в допуске ±1.5 с);
- **общие финальные титры** — не ложатся ложным «интро» (хвостовые голоса
  отброшены; тест «does not lock onto the shared end credits»);
- **чёрные фейды в середине** — не выдаются за концовки (run прижат к хвосту);
- **короткая чёрная вспышка в конце** (< 5 с) — не считается концовкой;
- **эпизоды без общего клипа** — детект возвращает пустоту, а не шум.

## Порог качества для интеграции

Для перехода от спайка к фиче (кнопка «Пропустить» / авто-skip) требуется
прогон пилота на **реальной выборке: ≥ 10 эпизодов из ≥ 3 сезонов разных
студий**, сравнение с метками TheIntroDB, и:

- precision по интро ≥ **0.85**, recall ≥ **0.80**;
- precision по концовкам ≥ **0.90**, recall ≥ **0.85**;
- средняя ошибка границы ≤ **5 с** (шаг сэмплинга 0.5 с + запас на монтаж);
- доля ложных «интро» из рекапов ≤ **10 %** эпизодов.

## Вывод

**GO — с обязательным гейтом.** Алгоритмическое ядро (dHash + офсет-голосование
для интро, хвостовой run титровых/чёрных кадров для концовок) на контролируемой
выборке даёт целевые метрики, устойчиво к разобранным ошибочным режимам и
укладывается в бюджет frame tap (≤32×32 сэмплы, ~2 fps, без ML). Стоит
продолжать: локальный детект — реальная замена ручным меткам там, где TheIntroDB
промахивается, и бесплатный фолбэк там, где меток нет.

Но «надёжно на реальных сериях» пока **не доказано**: все цифры — синтетика.
Поэтому go именно с гейтом: первый шаг follow-up — валидация на реальных
сериях по порогу выше; только после её прохождения — интеграция в UI. Если
порог не пройден — возврат к no-go и оставление TheIntroDB единственным
источником меток.

## Как повторить

```bash
npm run typecheck && npm test && npm run build   # метрики печатает tests/introDetect.test.ts
npm run tauri dev                                 # Меню настроек плеера → «Авто-детект интро (пилот #16)»
```

В `tauri dev`: включить пилот, досмотреть ≥ 2 эпизодов одного сезона
подряд — строка пилота показывает найденные сегменты, при закрытии каждого
файла в консоль devtools уходит JSON-отчёт (таймлайн-хэши для оффлайн-сверки
с TheIntroDB).
